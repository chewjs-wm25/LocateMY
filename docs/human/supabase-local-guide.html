本地 Supabase

LocateMY 组员操作说明

开始前 首次设置 日常使用 连接 Flutter 数据与迁移 命令速查 故障排查 安全边界

Team quick guide · Supabase CLI 2.117.0

在自己电脑上运行 LocateMY 后端。

本指南只处理本地开发：用仓库已锁定的 CLI 和 migrations 重建同一套 Postgres、Auth、Storage、REST API、Studio 与测试邮箱环境。

  • CLI 2.117.0
  • Postgres 17
  • Seed 已关闭
  • Docker 容器

开始前

  • 从仓库根目录操作；应能看到 package.json、supabase/config.toml 与 supabase/migrations/。
  • 安装 Node.js 20 或更高版本，以及 npm；这是通过 npm/npx 运行 Supabase CLI 的当前最低版本。
  • 安装并启动 Docker Desktop，或其他提供 Docker 兼容 API 的容器运行时；建议为 Docker 分配至少 7 GB 内存。
  • 首次启动需要下载多个镜像，请准备稳定网络与数 GB 磁盘空间。
不需要创建新的 Supabase 项目。仓库已经包含完整的 supabase/ 配置与按顺序执行的 migration；不要再次运行 supabase init。

首次设置

1

安装仓库锁定的 CLI

npm ci
npx supabase --version

版本应显示 2.117.0。以后都使用 npx supabase，不要依赖另一套全局版本。

2

确认 Docker 正在运行

docker info

若命令能显示 Server 信息即可继续。只有 Client 信息或连接错误，通常表示 Docker 引擎尚未启动。

3

启动本地 Supabase

npx supabase start

第一次会比较久；CLI 会下载镜像、创建容器，并依次执行 supabase/migrations/ 中的 SQL。

4

检查地址与本地密钥

npx supabase status

保存当次终端所显示的 API URL、Studio URL 与本地客户端 key，供本机调试使用。不要把终端输出中的 secret/service-role key 提交到 Git 或发到群聊。

日常使用

开始开发

npx supabase start
npx supabase status

重复执行 start 是安全的；已经运行时 CLI 会复用当前项目的容器。浏览器打开 http://127.0.0.1:54323 可进入本地 Studio。

拉取到队友的新 migrations 后

git pull
npx supabase db reset --local
db reset --local 会清空本地数据库。它随后会按顺序重放仓库 migrations。LocateMY 当前关闭 seed，因此重置后不会自动恢复你手工创建的测试账号或测试资料。

结束开发

npx supabase stop

普通 stop 会停止容器并保留本地数据卷；下次 start 可继续使用。

连接 Flutter 应用

应用必须通过运行时参数接收项目 URL 与本地客户端用的 publishable key。实际名称以组内 Flutter composition root 的约定为准，不要把 key 硬编码进 Dart 文件。

运行位置API 主机说明
同一台电脑上的工具http://127.0.0.1:54321可直接使用本机回环地址。
Android Studio 模拟器http://10.0.2.2:5432110.0.2.2 指向模拟器宿主机。
Android 真机http://<开发机局域网 IP>:54321手机与电脑需在可互访网络；防火墙须允许该端口。
客户端绝不能使用 service-role 或 secret key。Flutter 只能使用本地 status 输出中的 publishable 客户端 key；RLS 仍是数据访问边界。

本地邮件不会真的寄出。注册、验证或重设密码邮件可在 Mailpit 查看：http://127.0.0.1:54324。

数据、账号与 migration

创建本地测试账号

  1. 打开本地 Studio。
  2. 进入 Authentication 的 Users 页面，创建只供本机使用的测试用户。
  3. 需要查看认证邮件时打开 Mailpit。

本地数据与远端数据彼此独立。不要把真实个人资料或远端生产资料复制到本地。

需要修改数据库结构时

LocateMY 的 schema、RLS、View/RPC 与 Storage policy 由项目负责人按设计契约集中管理。组员先记录需求与受影响 Feature，不要在 Studio 手工改表，也不要自行编辑已经提交的历史 migration。

经明确分配后，新 migration 必须由 CLI 创建：

npx supabase migration new <简短英文名称>

完成后以 npx supabase db reset --local 验证从零重放。暴露 schema 中的表必须显式检查 GRANT 与 RLS；本项目的 auto_expose_new_tables = false，新表不会自动开放给 Data API 角色。

目的命令影响

常见故障排查

Cannot connect to the Docker daemon

先启动 Docker Desktop/引擎，再运行 docker info。Remote SSH 场景中，Docker 必须运行在执行命令的远端主机上。

supabase start 健康检查失败

npx supabase stop
npx supabase start --debug

检查报错服务、端口占用、Docker 内存与磁盘。不要连续盲目重试；保留首个明确错误给项目负责人。

端口已被占用

LocateMY 使用 API 54321、数据库 54322、Studio 54323、Mailpit 54324。先停止占用端口的其他本地 Supabase 项目，不要随意改 config.toml，否则两名组员环境会分叉。

migration 执行失败

记录失败文件名、SQL 错误和你当前的 Git commit。不要跳过 migration 或直接在 Studio 补改；把证据交给 migration 负责人修正后，再重新执行本地 reset。

想完全清除本地容器数据

npx supabase stop --no-backup
这是破坏性操作。它会删除当前项目的本地数据卷。只有确定不需要本地测试账号和资料时才执行；不要附加 --all。

安全边界

  • 日常组员只操作本地环境；远端 link、push、reset 与数据导入由项目负责人统一执行。
  • 绝不运行 supabase db reset --linked；该命令会清空已连接的远端数据库。
  • 绝不提交 service-role key、secret key、access token、数据库密码或包含它们的终端截图。
  • 不要改写已有 migration 历史；新增变更必须创建新 migration 并完整 reset 验证。
  • 不要依赖本地 Studio 的手工 schema 变更；它们不会自然成为队友可重现的仓库状态。
  • 本地堆栈只有开发用途：无 TLS、默认凭据且未按生产环境加固，不可暴露到公网。
收工检查确认代码没有新增密钥文件，git status 只包含你预期的变更，并使用普通 npx supabase stop 保留本地资料。

项目配置来源：package.json、package-lock.json、supabase/config.toml 与 supabase/migrations/。流程参考 Supabase 官方的 CLI 安装与运行及本地开发工作流；命令以仓库锁定的 CLI 帮助为准。
