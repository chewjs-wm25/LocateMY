# 各 Wave 开发与完成判定规范

> 状态：项目负责人已确认；2026-09-16；Java 阅读习惯约束补充确认于 2026-09-17
> 适用：所有 Wave 的 Feature、shared module、开发任务和实现审查。

本文件是开发流程与完成判定的唯一规则源。架构定义以
[技术架构](system/architecture.md)为准，产品行为与公开 Interface 以 owning Development Contract 为准。
本规范细化现有 `Implemented` / `Integrated` 流程，不改变产品范围、Interface 或数据模型。

## 1. 开发前固定验收范围

1. 读取 owning contract、相关上游公开 Interface、架构和事实源，确认 Ready Gate。已有 Ready contract 首次按本规范开发时，先补齐下面的验收分配；设计就绪状态不等于实现完成。
2. 在 owning contract 中为每项验收场景分配本模块验证、联合验证或两者都有。联合场景拆出当前模块应验证的行为，完整场景保留到期联合验证。
3. 每项记录依赖、证据要求、负责 Owner、最迟 Wave，以及本模块证据和联合证据的各自状态。依赖按本期真实接入、测试 fake、后续 Wave 槽位分类。
4. 所有验收场景均已分配、当前责任无歧义、后续事项有负责人和期限后开始实现。发现规格缺口时停止受影响部分，继续独立可执行部分；新增要求按现有范围/契约变更协议处理。

建议验收表结构：

| 场景 ID / 可观察结果 | 验证归属 | 所需依赖及用途 | 证据要求 | 负责 Owner | 最迟 Wave | 本模块证据/状态 | 联合证据/状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 契约场景或其本模块子项 | 本模块 / 联合 / 两者 | 本期真实 / 测试 fake / 后续槽位 | 测试、开发环境、设备或联合流程 | A/B；联合项指明主责及参与者 | 明确编号 | 待验证 / 已通过 + 引用 | 不适用 / 待接入 / 已通过 + 引用 |

## 2. 实现架构与依赖

以 Authentication 的分层作为实现参考：View 绑定状态与用户意图；ViewModel 管理呈现状态与交互；Application use case 编排行为；Domain 定义领域规则和类型；Data Adapter 实现 Application seam 并隔离外部 SDK。composition root 注入实现。

依赖方向遵循技术架构中的 `View → ViewModel → Application use case → Domain/Application seam ← Data Adapter`。跨模块只消费唯一公开入口。shared module 没有页面时只保留所需层；内部类名、文件数量和 helper 拆分由实现者决定，分层责任与依赖方向才是架构验收依据。

提供方先交付公开 seam，再实现真实 Adapter；消费者通过同一 seam 使用 fake 独立开发。本期负责的上游真实依赖须接入。后续 Wave 槽位可使用明确标识的占位页面或开发 harness，并登记接入责任与期限。开发运行入口也须满足适用的账户门控、权限和隐私屏障。

## 3. 本模块实现门槛：Implemented

实现者仅在以下全部适用项通过后声明 `Implemented`：

- 本模块承担的生产行为、公开结果、生命周期与副作用已经真实实现；当前责任路径可运行，无待实现骨架或以 fake 替代本模块生产能力。
- 验收分配中所有本模块项通过；正常、空/部分、失败、离线/权限、恢复及并发/过期响应按契约验证。联合场景的本模块子项也有当期证据。
- 有页面的模块已验证页面交互及契约要求的可访问性、本地化；无页面的模块通过公开调用入口验证。设备证据遵循设计入口的目标设备要求。
- 外部 Adapter 有确定性测试验证错误、边界和恢复，并有开发环境中真实调用的关键成功路径及适用权限证据。HTTP mock 或 fake 通过不能替代真实环境验证；数据对象及 Storage 的适用 allow/deny 证据也须补齐。
- 格式检查、静态分析、测试和 debug APK 构建通过，遵循现有 PR/CI 要求；证据注明命令或操作、环境、结果及对应代码版本，可追溯且无敏感凭据。
- 本次新增或修改的手写 Dart 代码已按第 7 节完成可读性审查；保留特殊写法的必要原因已说明。
- 当前模块实现验收阻塞为零，后续联合事项均有 Owner 和最迟 Wave。

优先通过现有最高公开 seam 测试可观察行为，避免为每一层强制新增测试缝或逐层重复测试。Adapter 验证真实映射，消费者验证其调用行为；两者都有责任。

外部环境不可用或证据缺失时，报告“实现已写完，验收阻塞”，补齐证据后才判为 `Implemented`。未来消费者未接入且未到联合验收期限时，记录为后续集成项。

## 4. 集成与 Wave 门槛

每项联合场景在预先指定的最迟 Wave，由负责 Owner 接入相关真实模块并完成联合验证。fake 证据用于独立开发，真实模块间的调用、生命周期、副作用及失败恢复需联合证据。

**Wave 完成 = 本 Wave 所有模块达到 `Implemented`，且截至本 Wave 到期的接线与联合验收全部通过。** 到期范围包括以前 Wave 留给本 Wave 的事项。未来事项按计划保留；存在过期事项时当前 Wave 未完成。

模块实现状态与集成状态分别记录。`Integrated` 仍由项目负责人完成跨 Owner 验收后批准；本期联合验收通过或 Wave 完成不自动授予所有模块 `Integrated`。完整契约联合场景未全部通过时，保留具体待接入项。

## 5. 审查与完成报告

审查先确定当前模块及 Wave，读取验收分配，再按证据判定。每个当前阻塞都引用未满足的验收条款或本规范门槛，说明缺口与解除条件。新发现的真实缺陷按适用契约判断；新增产品要求走范围变更流程。

每次完成报告固定输出：

1. **模块实现**：`Implemented` 或未完成；逐项关联验收证据。
2. **本期集成**：截至当前 Wave 到期的联合场景是否通过，列证据；无到期项则写不适用。
3. **后续集成**：待接入项、负责 Owner、最迟 Wave。
4. **当前阻塞**：具体缺口、对应条款和解除条件；没有则写“无”。

当前任务是否完成按其明确范围判定：模块开发按第 3 节，Wave 交付按第 4 节。本模块可为 `Implemented`，同时本 Wave 因到期集成而未完成。

## 6. Authentication 边界示例

Authentication 在 Wave 1 负责认证、当前设备会话、类型化结果和自身页面。Shell 的导航与门控、Privacy 的私有数据清理及 Account Center 的消费行为分别归其 owning contract。

Authentication 可以先验证自身恢复、登录、注册、确认状态、退出及失败映射，再由后续 Wave 补齐联合场景。其 mock HTTP Adapter 测试与页面 fake 测试是独立证据，真实开发环境验证仍需满足第 3 节。本示例不宣告现有 Authentication 已通过全部门槛，也不替既有联合场景指定期限；期限在开发前的验收分配中明确。

## 7. Java 阅读习惯与 Dart 可读性约束

目标是让熟悉 Java 的项目负责人容易理解代码：在功能和调用方式保持不变的前提下，优先显式、顺序清晰的写法，以及职责明确的对象协作。本节是该约束的唯一规则源。

### 适用范围与优先级

- 适用于新增和本次修改的手写 Dart 代码，包括生产代码、测试、fake 和开发工具；新的公开 declaration 设计也遵循本节。历史代码随相关任务逐步改善，此次只更新规范，不批量重构。
- 生成代码沿用生成器输出。优先满足行为契约、类型与空安全、生命周期、不可变性、SDK 要求及现有 formatter/analyzer 检查，再选择更贴近 Java 阅读习惯的等价实现。
- 保留现有方法/构造函数名称、参数名称与类型、命名或位置参数形式、默认值、返回类型、属性访问方式及可见性。结果、失败、副作用、执行顺序和异步行为同样保持不变；公开 Interface 变更仍走现有变更协议。

### 类型与控制流程

- 方法签名、字段和局部变量优先显式类型；不可变绑定继续使用 `final`，如 `final String accountId = account.accountId;`。遇到不可直接命名的推断类型等必要情况可保留类型推断。
- 方法、Getter、Setter 和有逻辑的回调优先使用完整 `{ ... }` 函数体与显式 `return`；条件和循环使用花括号。
- 优先 `if/else`、普通 `switch` 语句和 `for` 循环，使用命名局部变量表达中间结果。展开嵌套三元表达式、多步集合链、cascade 和复杂集合构建；模式解构优先改为清晰的类型判断或类型匹配后普通属性读取。
- 保留 sealed/final 类型和编译器提供的穷尽检查。替换模式或 switch 表达式时仍需覆盖全部结果分支；等价展开会损失类型安全或穷尽检查时，保留原机制并解释用途。

### Constructor、Getter 与 Setter

- 构造函数优先写明参数类型及字段初始化关系。保留命名参数、`required`、`const`、默认值和父类初始化语义；`final`/`const` 字段使用 Dart 初始化列表，避免为模拟 Java 构造函数体赋值而改为 `late` 或可变字段。
- 例如 `const Account({required this.id});` 可展开为 `const Account({required String id}) : id = id;`，保持字段 `final String id;` 及 `Account(id: value)` 调用方式。
- 现有 `model.state` 属性接口继续使用 Dart Getter；新接口默认也采用属性接口。显式 Getter 的写法为 `State get state { return _state; }`，不为模仿 Java 改成 `getState()` 或新增重复入口。
- 简单数据对象可继续使用公开 `final` 字段；仅为明确的封装需求引入私有字段和 Getter。Setter 只用于确实可变且需要控制写入的状态，使用完整函数体保留校验和通知语义，例如 `set value(String value) { _value = value; }`。不可变结果与状态快照继续保持只读；业务动作由具名方法表达。

### OOP 与必要的 Dart/Flutter 写法

- 沿用第 2 节的分层；让对象持有相关状态和行为，通过构造注入、接口与组合协作。按职责划分类和方法，不为形式增加继承层、包装类、空层或测试缝。无状态纯计算可保留清晰的函数。
- 保留空安全、泛型、`async/await`、`Future`、`Stream`、`const`、SDK callback、Widget 树和框架生命周期等必要机制。复杂回调或 Widget 构建按职责提取具名方法或组件；简单声明式构建可保留 Flutter 写法。
- 采用语法展开前检查求值次数、短路与惰性行为、异常传播、异步顺序和对象身份等语义。保留必要特殊写法时，在附近注释或审查说明中简述必要原因，不逐行解释常规框架语法。

### 审查与验证

审查覆盖本次新增和修改的手写代码：类型和流程是否明确、构造初始化是否清楚、属性调用与只读/可变语义是否保持、对象职责是否符合分层、必要特殊写法是否有理由。可安全展开的偏离应在本次修改中纠正；有明确必要原因的例外符合本规范。未修改的历史风格不单独构成本期阻塞。

行为改写复用现有最高公开 seam 的测试，验证结果、失败、生命周期、副作用及适用的异步/边界行为；按改动风险补充缺失场景。沿用格式、分析、测试和构建要求，不为语法风格新增运行时测试或新的测试缝。本次规范更新仅检查文档与链接。

语言规则参考：[Dart Constructors](https://dart.dev/language/constructors)、[Dart Methods / Getters and setters](https://dart.dev/language/methods)。这些参考解释语言机制，本节定义项目取舍。
