# 人类开发工作包规范

工作包把锁定的系统与 Feature 设计投影为能力较弱的实现者也能顺序执行的中文施工说明。它是
一次性派工产物，不是第二套设计真相；模板见 [`_template.md`](_template.md)，实际工作包保存到
`docs/human/`，且只在用户明确要求时读取。获项目负责人批准的 PDF 工作包与其余 `docs/` 一同
提交至 GitHub；组员从该仓库取得当前发布版本。

## 生成条件

只在以下条件全部满足时生成：

- 系统设计已 `Baselined`；
- 对应 Feature/shared module 已 `Ready for Development`；
- 所有直接阻塞项已完成；
- Owner 和实现者已经由项目负责人指定；
- File Manifest、Symbol Plan、测试场景和允许修改范围完整。

## 转换步骤

1. 锁定源设计的提交或版本，只抽取本次任务关联的 Capability、契约、文件和验收场景。
2. 将设计关系改写为按依赖排序的操作清单；每一步以可观察结果作为完成条件。
3. 对每个文件列出精确路径、动作、计划符号、责任和禁止越界项；不生成任何代码。
4. 用白话解释输入、输出、状态和错误处理，并链接完整权威契约。
5. 列出由学生亲自编写的测试场景、已有命令和手工验收步骤。
6. 列出可自行决定的局部实现与必须停止上报的设计问题。
7. 核对所有内容均可追溯到锁定源，不在工作包中产生新决定。

转换完成条件：实现者无需重建跨 Feature 设计即可开始，但仍需亲自决定和编写具体实现；工作包
不存在可直接提交的代码，也没有与权威设计冲突或无来源的要求。

## 生命周期

状态为 `Active → Implemented → Integrated`，或在来源发生相关变化时转为 `Invalidated`。
实现者可以声明 `Implemented`；只有项目负责人可以批准 `Integrated`。已集成工作包可以保留为
大学项目过程证据，但不继续维护，未来理解系统仍读取权威设计。

## 文件边界与协作

- `allowed`：实现者可在任务分支中创建或修改。
- `shared`：由项目负责人维护；实现者只能提交设计问题。
- `prohibited`：本任务不得修改。

两名学生使用独立短期分支。共享基础能力先整合，下游工作随后开始；项目负责人负责
composition root、共享接线、migration 顺序和最终整合。每个波次均执行受影响 Feature 与跨
Feature 测试。

## 设计问题格式

实现者遇到规格缺口时记录：当前工作包和步骤、相关文件或 Interface、期望行为、实际阻碍、
已尝试方向、是否阻塞及可能影响的其他 Feature。停止受影响部分，但可继续无关工作。只有项目
负责人批准后的设计变更才进入权威文件；相关工作包随后重新生成。
